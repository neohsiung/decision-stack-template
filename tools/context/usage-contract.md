## 決策棧使用契約（什麼時候檢索、怎麼造查詢句）

<!-- 正本。SPEC §使用契約 只留指標。各 harness 的保證載入通道 import 這一份，
     所以它要對不知道這個 repo 存在的 session 自足。接線清單見 MANIFEST.tsv。 -->

判斷原則的正本在決策棧 repo，三層：`Models/` 放少數不變的信念，`Frameworks/` 放思考與作業
骨架，`Decisions/` 放由事件揭露的判斷原則。三層之外還有 `Expressions/`，它不是第四層，裝的是
一格產出該用什麼詞、什麼語氣、放哪些內容，以及可以照抄的骨架。索引在 `MEMORY.md`。檢索用：

```bash
stack recall --expand "<一段話>"
```

`stack` 是這個 repo 的 CLI。`stack install` 會把它 symlink 到 PATH 上，任何工作目錄都叫得動。
叫不動時跑 `stack doctor` 看接線。

它掃全部條目，回 top-k 加一跳連結鄰居。覆蓋率由程式迴圈保證，不靠人記得有沒有讀完。

`--expand` 把每筆命中的機器層一起印出來：規則句、步驟、判準、邊界。拿到就能照做，不必再開檔。
人層（事件、為什麼、來由）是給 review 用的，要看時跑 `stack show <條目> --for human`。

### 兩個觸發時機

1. 接到任務時。提出 plan、做設計判斷、給出需要下判斷的回覆之前。
2. 動作成形的那一刻。正要下筆寫留言、寫文件、送訊息之前。

第二個時機常被跳過，而它檢索到的東西跟第一次不同類。約束產出形狀的原則，例如寫多長、寫給誰、
只寫增量，在第一次檢索時檢索不到。那時查詢句還在描述任務，不在描述「正要寫一則留言」這個動作。

`Expressions/` 就是為第二個時機準備的。查詢句要講出正在寫的那份東西是什麼、給誰，才撈得到
那一格的規格與骨架：「正要用即時訊息通知上級一件已經決定的事」撈得到，「這個專案的溝通策略」
撈不到。

### 決定成形時提議寫日誌

一個回覆或計畫定案了某個決定，而這個決定的結果幾個月內會揭曉，agent 在那則回覆的結尾提議
寫一筆決策日誌，由使用者決定寫不寫。人事、方向、長期投入、大額承諾，以及帶著預期效果的門檻或
規則調整，都算。日常小決定不提，提太多使用者就不會回看。

使用者說要寫，就走 `decision-journal` 這條流程。說不寫，這個決定就不再提。

理由：日誌的寫入是事件觸發，下決定的當下沒有任何東西會提醒。回看那一環有每日的到期檢查，
寫入那一環沒有入口，迴圈就只剩後半，日誌會一直是空的。當下漏掉的，由 `stack journal due` 補抓：
最近 7 天沒有新日誌時，它會多印一行提問。

### 查詢句用動作造，不用主題造

| | 例 |
|---|---|
| ✗ 主題句 | 「GTD 今天到期任務盤點與處理方式」 |
| ✓ 動作句 | 「把查證結果寫進哪張單子、要不要替負責方定實作規格」 |

主題句檢索到任務領域的原則。動作句才檢索到約束產出形狀的原則。

### 下筆前先寫「對象＋他缺什麼」

要離開對話的產出，例如留言、票面、文件、訊息，下筆前先寫一行。這一行不進交付物：

```
對象：<具名的人或角色> ｜ 他還缺：<1-3 項>
```

然後只寫那幾項。

讀者還不存在時，例如未來接手的人、未來的組織、未來的自己，對象寫那個角色，他還缺的就填
「現在只存在寫的人身上的東西」。

理由：查證完直接下筆時，內容會跟著「查到什麼」走，不會跟著「讀者缺什麼」走。「有考慮過讀者」
這件事沒有可失敗的檢查，寫的人可以自我認證。先寫這一行，就有了可以對照的東西。

兩條推論：

- 查證產物預設不進交付物。規格對照表、推論鏈、檔案清單、確認過程留在對話裡。只有會改變
  讀者下一步動作的那句進交付物。
- 自檢問句是「砍掉這段，讀者的下一個動作會不同嗎」。答案是「不會」就砍，即使它正確、而且
  剛花了時間查出來。

字數與段數不訂上限。寫多短屬節奏，寫成條款會產生機械擺盪。這一節管的是下筆順序與內容選擇。
判準一句話：產出的內容是收件人需要知道、而且還不知道的那部分。

棧外的寫作 skill 若給了閱讀時間預算，那不牴觸這一條。**超時是拆主題的觸發器，不是砍字的
指標。** 那種條款問的是「這份文件是不是塞了多個主題」，處置是拆；這一條禁的是把「寫多短」
訂成數字。兩者管的是不同的東西，同一個 session 兩份都載入時不必二選一。

### 即時訊息先抽口吻樣本

回私訊、對話串、多方討論串之前，先做兩件事，再下筆：

1. 讀整串。至少讀到對方上一則，找出他問的那一句。
2. 抽使用者自己在同一個對話寫的幾則訊息，存成口吻樣本檔。同一個對話找不到時，改抽他寫給
   同一個人的。樣本裡不放 agent 代寫的訊息，`stack prose --ref` 會依送出時的紀錄排除。

下筆時先回答他問的那一句，用他的說法。推理過程、查證過程、誤判的原因預設不寫，對方問了
才寫。要講的事多時拆成幾則送，不合成一則報告。

理由：只知道「對象是誰」寫不出像人的訊息。口吻的範本就在串裡，不讀就會退回文件的版型，
而文件版型在對話裡讀起來像系統通知。這一步寫在契約裡，不只寫在 Expression 裡，因為後者要
檢索剛好撈到才會執行。

這一節同樣不訂字數，靠樣本對照，見下一節。

### 送出前量一次

```bash
stack prose <檔案>
```

它印句數、句均字數、超過 40 字的比例、句中破折號密度，並拿本棧條目的同一組數字當對照。
條目都經過同一份寫作契約，所以那一行就是這套規則做得到的樣子。差距大代表契約沒有跟著這份
產出走。

即時訊息改拿口吻樣本當對照：

```bash
stack prose <草稿> --ref <樣本>
```

本棧條目是文件文體，拿它當訊息的對照線，會把訊息往文件的方向拉。給了 `--ref`，對照線改用
樣本現算的數字，另外印每則幾行、幾字、幾行是編號、條列、粗體、段落標籤這類版型。

**這跟上一段不衝突。** 上一段說的是不要訂字數條款，而這一支印的是量測不是條款：它不判及格
與不及格，也不給上限，只把兩組數字放在一起讓人讀。訂一個沒有根據的字數會產生機械擺盪，
量一次不會。

### 留痕

plan 檔或設計提案的第一行貼 `recall` 輸出的最後一行，格式是
`決策棧檢索：<ISO 時戳> 命中 …`。它由工具產出，偽造不了。沒有這一行等於沒檢索。跳過檢索
不會留下任何痕跡，跳過十次跟做到十次看起來一樣。這一行是唯一能事後看出來的欄位。

**大改之後要重貼。** 一份計畫可以改三輪而那一行不動，它仍然為真，只是早就不是這份計畫的
檢索紀錄。時戳就是為了讓這件事查得出來：

```bash
stack trace <檔案>
```

它印留痕行的檢索時刻、檔案最後修改時間、以及那個時刻之後又檢索了幾次。有更晚的檢索就代表
這一行不是最新的那一次。它不判定幾天算太舊，那是判斷，不是可數的事實。

**要離開對話的產出也要留痕，做法是先落成檔案。** 訊息、留言、票面沒有機械攔截點，送出那一刻
不經過任何工具，所以第二個觸發時機到底有沒有發生，事後查不出來。草稿寫進一個暫存檔就換到查得
出來的那一側。第一行貼留痕行，第二行貼〈下筆前先寫「對象＋他缺什麼」〉那一行，然後：

```bash
stack trace <草稿檔>
stack prose <草稿檔>
```

`trace` 缺留痕行時回非零，那就是原本沒有的那個訊號。兩支都不判及格，它們只讓跳過這件事留下
痕跡。草稿檔用完即棄，不進 repo。它存在的理由只有一個，讓第二個觸發時機跟第一個一樣查得出來。

這一步同時讓〈下筆前先寫「對象＋他缺什麼」〉那一行留得下來。那一節說過，有考慮過讀者這件事
沒有可失敗的檢查；寫進草稿檔之後它至少查得到，跟留痕行在一起。

### 三條使用規則

不把 `MEMORY.md` 整份讀進 context。覆蓋率的保證要來自程式迴圈。省下的 token 是附帶效果。

檢索到的要真的拿去解讀後面每一個輸入。檢索到不等於用上。把原則歸檔成背景資料而沒有拿它
判斷，等於檢索沒發生。反方向也一樣：檢索到的原則還沒驗過適用條件時，不能拿它推翻第一手觀察。

找到相關先例就往那個方向靠。沒找到就正常判斷，不要因為沒找到就停下來問。

### 撈錯或沒撈到時

實際工作中發現 `recall` 該撈到的沒撈到、撈到的不對題，或一筆條目的 `field` 標錯，照這三步：

1. 把查詢句、期望的條目、實際命中的條目講給使用者，提出修法。修法可以是改 description、改 field、
   拆條目或補新條目。
2. 等使用者裁決再改。改動照寫入程序走分支加 PR，不批次整理，也不為了這一筆加工具功能。
3. 那一題用原話加進 `tools/regression.tsv`，有領域的標第三欄。真實的漏撈題是證明過濾與檢索有沒有
   變好的唯一證據。

理由：條目的判準靠真實案例校準。先寫好規則再批次套用，錯誤會同時出現在幾十筆上，而且不產生訊號。

### 降級
