## 決策棧寫入程序（正本）

<!-- 正本。SPEC §寫入程序 與 §兩道閘門 只留指標。各 harness 的保證載入通道 import 這一份。
     跳過它不會有訊號，所以不能只放在 repo 裡等人來查。 -->

所有來源共用這一份。來源之間只帶四個參數進來：`origin` 值、commit 前綴、要不要寫 mem0、
能不能 push。程序不為每個來源各寫一份。兩份會各自演化，去識別化檢查的嚴謹度會先分岐。

跳過不會有訊號的是三步：step 3 基準閘門、step 4 dedupe、step 7 分支加 PR。

1. **判定門檻。** 依該來源的門檻節，見 [來源標記](source-marking.md)。不成立就不寫，也不在
   回覆裡報告「考慮過但沒寫」。
2. **去識別化。** 逐項檢查，不是讀過一遍。兩組問題，判準見 SPEC §去識別化判準。
   - 第一組問名字：無同事姓名含英文暱稱；無專案代號、內部系統名稱；無營收、人力、客戶數字；
     「某次在 X 系統因為 Y 專案發生的事」已寫成「當 <情境類型> 發生時」。
   - 第二組問時空：換一台機器、換一個人，這句話還成立嗎。
   - `downstream:` 欄位一併檢查。那裡放的常常是組織側產物的名字。
3. **定層加基準閘門。** 依 SPEC §內容分層 決定 `Models/`、`Frameworks/`、`Decisions/`，然後
   向上追問。

   要寫的是**一格產出的用詞、語氣與內容取捨**時走 `Expressions/`，不走這道閘門。它不在推導鏈上，換的閘門是
   軸必填：對象的方向與權責，加上渠道。填不出來就是這條規格還沒收斂到一格，不建檔。軸定位
   它在哪一格，檢索走 `description`，所以那一行要寫出這一格的情境。棧外已經
   有一份被執行的模板時，骨架節不抄全文，寫路徑加差異，理由見 SPEC §內容分層。三層的追問是：
   - 新 Decision 問兩題：這條判斷走的是哪副骨架？那副骨架背後是哪個信念？兩題都要有答案。
     新 Decision 一律經 Framework，直掛 Model 不合規。既存直掛 Model 的條目留給 curation
     逐步補，不追溯判違規。
   - 新 Framework 問一題：它由哪個信念長出來？

   答案到位才建檔。答案可以是既有條目，或本輪一併建立的上游。這是閘門，不是提醒。答不出時：
   - 使用者在場：把候選攤開討論。合法結果有三種：掛既有、當場抽新上游、使用者明示裁決留孤兒。
   - 非互動情境：寫進 `Pending/` 暫存待議。`Pending/` 不是第四層，不進 `MEMORY.md`，不被
     `stack` 掃描。回報裡列出待議的基準問題。下一個互動 session 先清 `Pending/` 再做別的寫入。

   這道閘門防的是「看到下了什麼決策就記什麼」。沒有它，Decisions 會累積，推導鏈不會自己長出來。
4. **dedupe，層感知。** 跑 `stack recall "<這條新規則>"`，讀它回傳的那幾筆與一跳連結鄰居。
   不讀 `MEMORY.md` 全文，也不把整個 repo 讀進來。

   `recall` 同時掃未合併分支。一條原則寫在一個分支上，會從工作目錄消失，這正是 dedupe 要防
   的事。分支上的條目標〔未審〕。引用時照實說它未審。然後分四種情況：
   - 同層語意等價：不建第二個檔。在既有檔的 `confirmed:` 追加今天日期。
   - 跨層有衍生關係：不算重複。上游那筆加 `downstream:`，下游那筆連回上游。
   - 近似但不等價：分開存。用 frontmatter `related:` 互相連結，寫出分界句。
   - 比既有多筆更上游：這是收斂的機會。寫成上游的通用模型，把既有那幾筆連上去當實例。
     dedupe 是逐筆比對，收斂是看整份索引的結構。只做 dedupe，條目會一直增加而判斷力不會。

   反方向的失效也要查：一筆條目服務了多個檢索情境。判準是單一職責原則的檢索版：一筆條目
   只能有一個「被檢索的理由」。拆分測試：說得出兩個情境，其中一個會用到 A 但完全用不到 B，
   就拆；說不出就一筆。同一句話拆成 Model、Framework、Decision 因此是合法的。軸在界定問題時
   被檢索出來，程序在執行時被檢索出來，觸發規則在事件發生時被檢索出來。

   收斂與拆分共用可重算的度量：`stack shape` 的群距離與 `stack eval` 的檢索吸子。升降級的
   完整判準以 SPEC §各層契約 為正本。
5. **寫入。** frontmatter 照 WRITING §frontmatter。正文分節與首句照 WRITING §寫作指南。
   內部連結用相對 markdown 連結，不用 `[[wiki-link]]`，這個 repo 不解析那個語法。不加 H1。
6. **索引加傳播。** `MEMORY.md` 對應分節加一行。沒進索引等於這條原則不存在，檢索端讀的就是
   這份索引。接著讀該筆的 `downstream:`，列出可能已經跟不上的下游產物交給使用者判斷。不自動
   改。下游多是給別人用的 skill 與制度文件。
7. **開分支、commit、開 PR。** 不直接寫 `main`。`main` 是已審的 trunk：

   ```bash
   cd "$(stack root)"
   git checkout -b <前綴>/<這次的主題>          # 例：judgment/gate-at-effect-boundary
   git add <明確路徑> MEMORY.md                  # 明確路徑，不用 -A
   git commit -m "<origin 前綴>: <那句可遷移規則>"
   git push -u origin HEAD && gh pr create       # 審查在 PR 上進行
   ```

   `-A` 在這個 repo 是去識別化風險。它會把工作區裡任何東西掃進來。

   push 並開 PR，不自己合併。分支停在本機等於審查請求永遠不會送出。審查閘門只看 PR。

   一個 PR 一個連貫的主題，以「最小的完整範圍」為單位。判準是合併之後系統自洽：只加工具不改
   契約等於沒生效，只改契約不加工具是壞的，這兩件事屬於同一個 PR。一條新原則跟一個工具修正
   沒有這種相依，就是兩個 PR。

   完整範圍有一個上限：一次 review 讀得完。批次整理不豁免。一輪整理產出多個小 PR，每個 PR
   一個異動類型或一個收斂組。審不完的 diff 等於沒有被審。

## 兩道閘門

跟來源無關，是獨立的閘門。

### trunk 閘門

寫入自動，但寫在分支上。`main` 只接受審查過的內容。

閘門架在內容開始生效的邊界，不在它離開本機的邊界。`stack recall` 讀的是工作目錄。
一條原則寫下的那一刻就已經在影響判斷了。把閘門放在 push 上，守到的是外流，守不到生效。

- 寫入一律走分支，命名 `<origin 前綴>/<主題>`。審查在 PR 上進行。合併後 `main` 才變動。
- `main` 的定義是「已審」，不是「最新」。
- 擋不住的那一段改成有訊號：分支上的內容照樣會被 `stack recall` 檢索到。那是對的，當輪寫下
  的原則本來就該當輪拿來用。工具標〔未審〕，引用時照實說。

沒有任何自動化路徑會合併 PR。「這段 diff 有沒有夾帶組織專屬內容」是一個判斷，不是一個檢查。
個人 repo 是 private，仍要當成可能會被看到來處理。去識別化是唯一可靠的防線。

未合併的分支數持續變大時，那是待辦不是狀態。報告要明說累積幾個與最舊一個的日期。

### mem0 鏡射閘門

只有 `origin: judgment_case` 寫 mem0。scope 用 `stack config mem0.scope` 查。那個指令回非零
就代表本機沒有設定 mem0，整節不適用，不問也不報告。

其餘來源不寫。否則「作者的判斷被外部糾正過幾次」這個數字會被自我發現與自我口述的條目稀釋，
而那是 mem0 這一側唯一想保留的訊號。

`MEMORY.md` 這一側才是完整集合，mem0 是補充。這是設計。看到 mem0 筆數遠少於檔案數時，
不用「把全部條目批次鏡像進去」來修。
